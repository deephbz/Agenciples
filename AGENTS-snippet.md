## Work OS Principles

Eight principles govern all research and engineering work here, because agents made implementation cheap and left human-governed intent, concept clarity, investigability, and continuity as the scarce resources. (1) **Full-stack traceability**: important computations must be investigable across abstraction layers — clean default output plus a trace/debug mode exposing intermediate state and provenance, with raw records kept as source of truth and every important claim anchored to an external verification signal (a trace or doc alone is not proof of correctness). (2) **Ontology-first design**: identify the domain's irreducible nouns, verbs, and relations before designing APIs or generating code; encode distinctions in types, not prose; a good ontology yields the smallest safe, stable public contract with few semantically stable verbs, schemas limited to the coordinates required for safe composition, and rich task meaning carried in agent-readable prose; that contract preserves caller intent, compatibility, and externally observable guarantees while implementations remain the agents' search space, so review interfaces harder than implementations. (3) **Artifact-first, backend-first**: work starts from a durable written problem artifact and ends with a durable result artifact whose canonical form is machine-operable (data + config + code version + interpretation) with visuals as derived renderings; version-control the full source bundle (code, configs, prompts, plans, evaluators — natural-language instructions needed for reproduction are source), persist final artifacts, and treat intermediates/retries as disposable unless they carry distinct experimental or audit value; normally keep one canonical generation, temporarily one useful predecessor while a candidate awaits ratification, then garbage-collect superseded runs; expose reasoning/data lineage as reviewable graphs; idea/data diagrams are authored and agreed before development and refreshed at each milestone (alignment devices for humans, teams, and agents — not after-the-fact documentation), and each project keeps a curated evergreen doc (decisions still in force, current status, blockers, next steps) separate from append-only journals — never let results live only in chat, screenshots, or one-off notebooks. (4) **Single source of truth, fluid representation**: every fact, spec, or procedure has exactly one authoritative home, which migrates as work matures — shaping-stage truth lives in docs and diagrams; once interfaces stabilize, specs move into types and public APIs and docs trim to intent, rationale, and pointers (a spec living in both doc and code means one is already stale); natural and programming language read the same to agents but differ in verifiability and reliability, so allocate deliberately and re-allocate as procedures harden (SOP doc → script → library), keeping docs and code pointing at each other; typed APIs carry intent into code, while actionable runtime outcomes carry stable identifiers and pointers back to authoritative guidance; physically, durable artifacts have only three canonical homes: repositories for reusable/versioned source, project-local workspaces for task-specific scaffolding, and shared artifact storage for durable/distributed outputs — temp and ad-hoc node-local locations are scratch only. (5) **One truth, baseline- and audience-fit projections**: keep one authoritative semantic record, then derive separate views for each consumer and starting point; agent turns are episodic, so before durable prose recover the audience, its accepted baseline, and the final accepted state, and write from those rather than from the sequence of agent turns; residue test: if a rejected intermediate state had never existed, would this explanation still be needed? if not, it belongs in historical evidence at most, never in current prose; model-facing content is validated, decision-complete, and economical with context; machine and trace records preserve exact structured state, provenance, versions, and receipts; human interfaces use hierarchy, progressive disclosure, comparison, visualization, and sound when useful; test each projection independently; projections can change form but must not invent domain state or become competing authorities. (6) **Stage-calibrated rigor ("where are we?")**: establish the project's lifecycle stage (shaping, exploration, consolidation, hardening, sharing) before choosing practices — infer it, ask when ambiguous, declare it in the evergreen doc; exploration wants glue scripts and fast insight to discover the right shape, extensive unit tests before the shape exists are tautological, and linters/formatters/CI/CD earn their keep only once work is functional, performant, and heading for a PR — stage lowers the formality of verification anchors, never their existence. (7) **Intent-preserving change composition**: before implementation, establish the exact base revision and inspect pending changes for overlap in files, interfaces, and concepts; treat semantic intent—not the workspace, branch, worktree, commit sequence, or agent turn—as the unit of change; amend refinements to the same intent, create or stack a distinct change for distinct intent, and escalate unclear ownership; review each isolated contribution relative to its base and dependencies, then verify it in the integrated result; rewrite toward the final accepted design, applying the residue test from (5) to the change itself: remove comments, compatibility paths, tests, or explanations that exist only because of a rejected intermediate design. (8) **Governing intent and scope**: every durable artifact carries a lightweight local governance envelope stating why it exists, what responsibility it owns, and the relevant boundaries, invariants, or non-goals that implementation alone cannot preserve; do not use this as tautological API reference; agents may freely optimize inside the envelope, but materially broadening, repurposing, or moving the envelope must be surfaced for deliberate human review — governance evolves, but never silently. Preserve three distinct information classes: historical evidence preserves source records and observations, which may be incomplete or wrong; current working context states what still matters and is corrected or superseded as understanding changes; assessments and projections state what we currently infer and must remain recomputable with provenance, freshness, and uncertainty. Scenario playbooks (module design, domain modeling, research artifacts, agent continuity, source allocation, semantic changes, governing intent/scope, stage calibration) live in the `work-os` skill; load it before non-trivial design, implementation, debugging, research, change review, or agent-workflow work.

Use risk-proportional change and verification. Compatibility is an explicit contract, not a default precaution: preserve it only for an accepted contract, a verified active consumer, or an explicit migration requirement; otherwise remove obsolete paths without aliases, shims, fallbacks, dual formats, or migration code. Before adding or repeating a check, name the plausible failure that it uniquely detects. Do not test declarations by restating defaults, constants, mappings, types, or direct delegation. Test meaningful behavior at the narrowest semantic boundary, and reuse unchanged verification evidence.
